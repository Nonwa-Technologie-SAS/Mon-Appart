# 0003 — Modèle physique PostgreSQL v1

Date : 2026-10-07

## Contexte

L'API NestJS n'avait qu'une migration activant PostGIS. Il fallait un modèle complet (identité, lieux, biens, annonces, médias, interactions, recherche, recommandation, confiance, notifications, audit, événements) qui tienne de quelques milliers à des millions d'utilisateurs sans réécriture, avec Prisma 7.10 comme outil de migration.

## Décision

1. **Bien et annonce séparés.** `properties` sans prix ni statut commercial ; `listings` pour l'offre ; `listing_prices` historise les prix ; `property_ownerships` historise les propriétaires.
2. **Clés.** `id` BIGINT en `GENERATED BY DEFAULT AS IDENTITY` sur les tables métier et volumineuses, INTEGER sur les référentiels. `public_id` UUID (`gen_random_uuid()`) est le seul identifiant exposé.
3. **Argent en NUMERIC(14,2)** avec une devise ISO 4217 par ligne (`XOF` par défaut). Pas de table des devises tant qu'une seule est utilisée ; un CHECK garantit le format.
4. **Coordonnées.** `latitude`/`longitude` NUMERIC(9,6) saisies, `geo_point GEOGRAPHY(Point, 4326)` générée et indexée en GIST. Une seule source, aucune divergence possible.
5. **`updated_at` par trigger SQL** (`set_updated_at()`), pas par `@updatedAt`, pour couvrir le SQL brut et les outils d'administration.
6. **Règles en base.** CHECK, unicités partielles et clés étrangères composites (`inquiries`/`appointments` → `listings(id, property_id)`) plutôt que des validations seulement applicatives.
7. **Tables à fort volume prêtes au partitionnement** : `property_views`, `searches`, `user_events`, `audit_logs` ont une clé `(id, created_at)` et un BRIN sur `created_at`. Elles ne sont pas partitionnées tant que le volume ne le justifie pas.
8. **Audit append-only** par trigger, sans clé étrangère vers l'entité auditée (`entity_type`, `entity_id`).
9. **Enums PostgreSQL** pour les états maîtrisés par le code ; **tables** pour les catalogues administrables (types de biens, équipements, lieux, rôles, permissions).
10. **Seed en deux profils** : `reference` (tous environnements) et `development` (poste local, refusé hors local), idempotents et sans suppression.
11. **Base de test dédiée** `*_test`, migrations réelles, tests en transaction annulée, reset gardé par script.
12. **Noms de migration horodatés** (convention Prisma) plutôt qu'une numérotation manuelle.

## Contournements Prisma

- `IDENTITY` et la colonne générée `geo_point` ont été écrits dans la migration initiale avant sa première application. `@default(dbgenerated())` sur `geoPoint` évite que Prisma y voie une dérive.
- Le prédicat de l'index partiel `listings_one_live_per_type_key` est écrit sous la forme normalisée par PostgreSQL (`status = ANY (ARRAY[...])`), sinon Prisma le recrée à chaque diff.
- CHECK et triggers vivent dans une migration SQL séparée ; Prisma ne les lit pas et ne les supprimera pas.
- Fonctionnalités preview : `partialIndexes`, `postgresqlExtensions`.

## Alternatives écartées

- **UUID comme clé primaire** : index plus gros et insertions dispersées sur les tables volumineuses. L'UUID reste l'identifiant public.
- **`owner_id` sur `properties`** : perd l'historique et l'indivision.
- **Prix sur `listings`** : perd l'historique, empêche les alertes de baisse de prix.
- **`DOUBLE PRECISION` pour les coordonnées seules** : pas d'index spatial ni de distance fiable.
- **Partitionnement dès maintenant** : complexité (clés, contraintes uniques, maintenance des partitions) sans volume qui la justifie.
- **Triggers métier** (calcul de score, statut d'annonce) : la logique reste dans l'application, la base garantit les invariants.

## Conséquences

- Les requêtes spatiales passent par `$queryRaw` ; le client Prisma ne lit pas `geo_point`.
- Toute nouvelle table avec `updated_at` doit créer son trigger (vérifié par `test:db`).
- Les identifiants internes sont des `bigint` JavaScript : ne jamais les sérialiser vers un client.
- `packages/types` suit désormais les rôles `CUSTOMER`, `OWNER`, `AGENT`, `AGENCY`, `MODERATOR`, `ADMIN`, `SUPER_ADMIN` et le type d'annonce `LEASE_TO_OWN`.
